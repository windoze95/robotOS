robotOS now keeps enough records to work out what happened after something goes wrong (#53).

**On the R1**
- robotOS keeps about a week of its own record:
  - recovery checks and how they ended;
  - the recovery cover showing, lifting or being swiped away;
  - radio cuts and restores, including failures;
  - screen, power and network changes;
  - voice-turn metrics.
- The record holds timestamps and outcomes only: no content, addresses or credentials. Read it
  over USB with `adb shell dumpsys activity service dev.r1ptt/.PttService`. No root is needed,
  and the output starts with the idle-drain summary.
- Android's log buffers grow from 256 KB to 2 MB. Before, a few minutes of logs survived once
  Tailscale started flooding them. The R1's Magisk module sets this at boot, and provisioning
  applies it at once. An R1 that's already set up gets it the next time the module is installed.

**On the hub**
- The hub keeps a week of each R1's check-ins, accepted or refused: the time, the result and the
  app version, never the request or a credential.
- The owner reads them with `GET /api/v1/devices/{id}/check-ins`. A gap shows when an R1 couldn't
  reach the host.

**In each release**
- Releases now include `mapping.txt`, R8's map back to the open source names, so a stack trace
  from an installed build can be read. `SHA256SUMS` lists it too.
- CI now runs once per change instead of twice per pull request plus again for each tag (#54).

Update the app and the hub. Each works with the other's older version. The hub change adds one
table and needs no migration, so rolling it back still opens the database.

Automated tests cover the following:
- the record rotating within two bounded files, newest last;
- the recovery cover's shown and lifted entries;
- a single radio-restore entry per wake;
- the hub keeping accepted and refused check-ins for the owner only, pruning them, and serving
  them over HTTP.

On a physical R1 running a signed 0.6.6 preflight with the updated hub, the record showed:
- the app starting;
- the network on Wi-Fi;
- the recovery cover shown and lifted;
- recovery checks answered in 0.1 to 0.6 seconds;
- the screen turning on and off;
- a 502 from the host while it restarted during the deploy.

The hub's history listed the same wake's check-ins.
