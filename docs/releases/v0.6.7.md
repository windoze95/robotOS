robotOS now works with Android's own lock screen, the recommended way to protect an R1.

Only Android's PIN protects the R1's data: its storage is encrypted with a key tied to the PIN, and
Android limits how fast anyone can guess. robotOS's recovery cover is not a lock; it can be
bypassed through debugging, safe mode or other Android screens. INSTALL.md has the three-step
setup: a PIN, "lock after screen timeout" set to 15 minutes to match robotOS's grace, and device
admin so marking the R1 lost also locks Android.

- **The button respects Android's lock.** While the R1 is locked, a press only wakes the lock
  screen; it still silences a ringing R1. Nobody can talk to Hermes, which can send texts,
  without the PIN.
- **Tapping to sleep no longer forces a lock.** With device admin turned on, robotOS used to turn
  the screen off with Android's immediate lock, so every tap would have demanded the PIN.
  It now uses the sleep key, so Android's lock-after delay applies. The immediate lock is kept for
  lost mode and as the fallback without root.
- **Open with this R1's PIN (#45).** When your host can't confirm a wake, the recovery screen
  offers to open robotOS with Android's own PIN screen. robotOS never sees or stores the PIN,
  Android's guess limits apply, and a lost, revoked or cleared R1 stays restricted. The host's next
  answer still applies: a lost reply takes the screen back at once.

App update only. The hub and Hermes tools are unchanged.

Automated tests cover the following:
- the button doing nothing while Android is locked;
- tap-to-sleep never calling the immediate lock when root works, and falling back to it without
  root;
- the PIN option opening an unverified R1 through Android's PIN confirmation;
- the PIN option never appearing for, or opening, a restricted R1 or one without a PIN.

A signed 0.6.7 preflight ran normally on a physical R1 without a PIN. The locked-button and PIN
paths need a PIN on the device, so they haven't been exercised on hardware yet.
